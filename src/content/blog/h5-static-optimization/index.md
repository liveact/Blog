## 背景

我们团队负责的是一套 H5 营销系统，核心能力是让运营人员在可视化编辑器中搭建营销页面——包括 H5 小游戏和抽奖活动。用户在编辑器里拖拽配置文本、图片、游戏组件，实时预览效果，确认无误后点击发布，页面就会上线供 C 端用户访问。

系统后端基于 Django，整体架构围绕一个核心概念展开：编辑态和发布态的分离。编辑时，前端通过接口动态获取数据；发布后，所有动态数据都会被静态化处理，脱离后端服务独立运行。

这套系统承载了大量营销活动，单个活动在推广期间可能面临数十万甚至上百万的访问量。如何在这种量级下保证页面秒开、后端不崩，是我们一直在解决的问题。

## 面临的问题

最初的版本里，C 端用户每次访问活动页，都会触发后端接口调用——拉取页面配置、游戏数据、抽奖信息。活动上线初期流量不大时没什么问题，但随着业务增长，几个瓶颈暴露得很明显：

- **接口压力集中**：每个 PV 都会请求后端获取页面配置数据，活动高峰期 QPS 直接打满 Django 服务。
- **数据库成为瓶颈**：页面配置存在数据库的 JSONField 里，大量并发读请求让 DB 连接池迅速耗尽。
- **抽奖场景更极端**：用户集中在活动开始的前几分钟涌入，抽奖接口不仅要读取奖品库存，还要更新中奖记录、扣减库存，读写混合的压力非常大。
- **发奖流程阻塞**：中奖后的发奖逻辑（发优惠券、推送消息、记录流水）如果同步执行，接口响应时间会被拉到几秒，用户体验很差。

这些问题的本质是同一个：不该让后端服务承担它不需要承担的流量。

## 解决方案

### 静态化：HTML 与 JSON 分离

这是整个优化的核心思路。我们把编辑态和发布态做了彻底的分离。

**编辑态（预览模式）**：前端编辑器中，用户修改配置后通过接口实时保存到数据库的 `config_json` 字段，预览时后端动态读取这个字段返回给前端。这个阶段只有编辑人员在用，并发量可以忽略不计。

**发布态（静态模式）**：点击发布后，系统会执行一套静态化流程：

1. 从数据库读取 `config_json`，序列化为静态 JSON 文件，上传到 CDN 存储。
2. 读取原始的 `index.html` 模板，将其中的动态接口引用替换为 CDN 上的静态 JSON 路径，注入资源 base 路径。
3. 处理后的 HTML 文件写入本地磁盘，由 Nginx 直接提供服务。

发布完成后，C 端用户访问活动页时，Nginx 直接返回本地 HTML 文件，浏览器再从 CDN 拉取配置 JSON 和图片、音频等静态资源。**整个过程完全不经过 Django 服务**，后端压力直接归零。

对于多页面游戏场景，逻辑类似但更复杂一些：系统会遍历游戏的所有页面结构，逐个生成对应的静态 HTML 和配置 JSON，并按版本号组织目录结构，保证每次发布的资源互不冲突。

### CDN 分发与资源去重

静态资源的存储设计上做了两层优化：

**MD5 去重**：游戏页面上传时，系统会计算压缩包的 MD5 值。如果该 MD5 已经存在，说明资源内容完全相同，就跳过文件存储，直接复用已有资源。多个游戏页面可以共享同一份静态资源包，显著节省存储空间。

**版本化路径**：配置文件按 `v2/game/{slug}/{version}/config.json` 的路径存储，每次发布生成新版本，既能利用 CDN 缓存又不会出现缓存不更新的问题。静态资源则通过 `game_page/{md5}/assets/` 路径永久缓存，因为 MD5 相同就意味着内容不变。

### Redis 缓存

抽奖组件是系统中少数仍需要后端实时处理的场景。我们用 Redis 做了多层缓存：

- **奖品库存**：活动开始前把奖品信息和库存加载到 Redis，抽奖时直接从 Redis 读取和扣减，避免频繁读写数据库。
- **排行榜**：用 Redis 的 ZSET 结构实现游戏排行榜，`ZADD` 写入分数，`ZREVRANGE` 获取排名，时间复杂度 O(log N)，轻松应对高并发查询。
- **活动配置缓存**：抽奖规则、概率配置等热数据缓存在 Redis 中，设置合理的过期时间，减少数据库查询。

### Celery 异步处理

中奖后的发奖流程天然适合异步化。用户抽中奖品后，接口只做两件事：扣减 Redis 库存、返回中奖结果。剩下的动作——发放优惠券、发送通知、写入中奖记录、同步库存到数据库——全部丢给 Celery Worker 异步执行。

这样抽奖接口的响应时间从几秒降到了毫秒级别。即使 Worker 处理稍有延迟，用户也不会感知到，因为前端已经展示了中奖动画。

## 架构设计思路

整个架构可以用一句话概括：**编辑走接口，访问走文件**。

编辑器面向的是内部运营人员，并发量低，走 Django 动态接口没有任何问题。发布这个动作本身就是一个天然的"编译"节点——把动态数据编译为静态产物，之后的所有 C 端流量都由 Nginx 和 CDN 承担。

对于抽奖这类必须实时交互的场景，则通过 Redis 把数据库挡在后面，用 Celery 把耗时逻辑推到后台。核心思路就是：能静态化的全部静态化，不能静态化的尽量缓存，缓存之后的写操作尽量异步。

## 优化效果

方案落地后效果比较明显：

- 活动页面访问完全不经过 Django，后端服务的 QPS 压力下降了 90% 以上。
- 页面加载速度依赖于 CDN 节点，平均响应时间从原来的 300-500ms 降到了 50ms 以内。
- 抽奖接口在万级并发下响应时间稳定在 50ms 左右，没有出现超时或错误。
- 数据库连接数从高峰期的满载降到了平时的 20% 以下，因为绝大部分读请求被 Redis 和静态文件消化了。

## 总结

回过头看，这套方案并没有用到什么新奇的技术，都是 Nginx、CDN、Redis、Celery 这些成熟的工具。关键在于想清楚一件事：哪些请求是真的需要后端处理的，哪些只是在浪费后端资源。

营销活动页面的内容在发布后就不会变了，完全没必要每次都走接口查数据库。把这个认知转化为架构设计——静态化 + CDN——就解决了 90% 的问题。剩下的 10% 是抽奖这类实时场景，用 Redis 和 Celery 兜底就够了。

做性能优化最重要的不是堆技术栈，而是理解业务的流量特征，然后把流量引导到最合适的地方去。
